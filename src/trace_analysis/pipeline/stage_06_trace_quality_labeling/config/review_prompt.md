# 06 证据复核指令（stage06-v1-draft）

输入：同一案例原始证据、冻结的标签/Rubric/证据规则、待审核标签版本及 review.schema.json。
先独立核对目标与原文，再对照拟议标签。记录是否看过初稿；模型复核不能声称人工确认。

逐项检查：
- 核心目标、需求形成时间与 Episode 边界是否一致；是否用局部反馈替代整体结局。
- 每个 claim 的引用真实存在、角色正确，且语义上支持该主张；工具索引不等于工具正文。
- 需求点/子需求点符合冻结表定义和边界；没有凭计划扩大映射；只知父级时保留 partial。
- gate 的 true/false/null 区分明确；完整性不等于成功；五维难度不是按步骤数量加分。
- 每个反馈针对什么要求/先前输出；新增要求、正常深化、纠错不能混淆。
- 需求级评估独立有据；Episode confirmed 不意味着每个需求有痛点。

输出 review.schema.json 的 accepted/corrected/unresolved；corrected 必须列出具体字段和前后值，
由运行器应用修正后重做 schema/引用校验并计算 hash。实际 reviewer_id、时间、输入/输出 hash
由运行器注入并核验，禁止模型编造这些元数据。信息不足用 unresolved 并说明补证内容。

逐个输出 claim_reviews，覆盖 reviewed_claim_ids，不重复 ID。每条标记 supported/partial/unsupported/unknown，并给出理由、依据和需要补取的信息。模型初标自述 supported 不等于复核已通过。不要因模型误引或漏引直接降低整个 Trace 质量；应修正标签或补证。

检查前三十三类是否至少有一个有证据支持的父需求；34–36不能替代主需求资格。
核对每项映射是否有独立依据，是否把助手计划和潜在流程都贴成需求；数量多只提示复核，不截断。
工作对象只选本案例实际涉及者，不因通用风险/上下文条目的候选对象多就全选。
